# Why `prettier --write` runs FIRST

`prettier --write` rewrites the staged file, and every line-anchored pragma — `@ts-expect-error`,
`eslint-disable-next-line`, coverage ignores — binds to *the next line*. A reformat that wraps a
guarded call inserts a line between the directive and its target, so the directive lands on a line
carrying no error and the real error escapes unsuppressed.

This file used to run `eslint` first and `prettier --write` second, which meant **both** checkers saw
a file the commit would not contain.

Measured 2026-09-10: `npx tsc --noEmit` exited 0, the commit landed, and CI was red on two required
jobs for the file that commit added. Adding a description eslint requires had made a
`@ts-expect-error` comment longer, pushing the guarded call past prettier's print width; prettier
then wrapped it across six lines. Nothing in either output distinguished "the check passed" from
"the check passed on a file that no longer exists".

Formatting first costs nothing and closes the eslint half of the class outright.

## Why `.test-d.ts` also gets `tsc --noEmit`

eslint cannot see a detached `@ts-expect-error` — that is the compiler's judgement, and
`reportUnusedDisableDirectives` covers only eslint's own directives. Type-level tests are where TS
pragmas live and where a detached one silently inverts what the file asserts, so those files pay for
a typecheck.

Scoped to that glob rather than all `.ts`, because `tsc --noEmit` is whole-project either way
(~37s measured on this repository) and the glob decides only how OFTEN that is paid. A hook that
costs 37 seconds on every TypeScript commit is a hook people pass `--no-verify` around, which is the
same outcome as not having one.

## Not covered, stated rather than implied

An `eslint-disable-next-line` detached by a reformat in a file eslint does not lint, and any pragma
in a file type outside these globs. The ordering fix closes the common case; it is not a proof.
